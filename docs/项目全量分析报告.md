## 1. 一句话结论

这是一个**工程质量远高于同类的 Minecraft 客户端 UI 动画模组**：单一 jar 双加载器（Fabric + NeoForge）、17 个 Mixin 全部用完整描述符、出厂 `defaultRequire: 0` 优雅降级、三层验证（真实 Mixin 引擎注入 / 桩类离线状态机 / 真机截图测量）、并且把踩过的坑逐条写进 README。

它现在的主要问题**不是 bug，而是增长方式**：功能状态寄存在一个 1456 行的全局静态类里，第三个功能会开始出现"改 A 坏 B"。这正是本次架构设计的动因。

## 3. 运行时架构（当前实现）

### 3.1 渲染管线的三个真实约束

这套模组全部设计都建立在 26.3 GUI 管线的三个事实上，**它们是架构的输入，不是可优化项**：

1. **界面分两层提取**
   `Screen.extractRenderStateWithTooltipAndSubtitles` 依次调用
   `extractBackground(...)`（变暗遮罩 / 模糊 / 菜单底衬 / 容器底板 / 槽位背景 / 字幕）
   → `extractRenderState(...)`（物品 / 文字）
   → `extractDeferredElements`（提示框）。
   两层要各自包一层矩阵平移，否则会出现"物品在动、底板硬邦邦"。

2. **物品是提交阶段才画的**
   屏幕内容在**提取阶段**录制成渲染状态（`BlitRenderState` / `ColoredRectangleRenderState` / `GuiTextRenderState` / `GuiItemRenderState`），物品图标则在**渲染阶段**由 `GuiRenderer.submitBlitFromItemAtlas` 从图集提交。
   → 物品透明度必须在提取阶段"登记"、提交阶段"套用"，这是 `ITEM_ALPHAS` 这个 `IdentityHashMap` 存在的唯一理由。
   → 画中画（背包布娃娃 / 附魔书 / 地图 / 旗帜）更极端：提取阶段产出状态，渲染阶段 `blitTexture` 才贴回，且 `PictureInPictureRenderState.pose()` 恒为单位矩阵。

3. **颜色 alpha 在构造渲染状态时就被"烘"进去**
   所有淡变都是 `@ModifyVariable(ordinal=N)` 改构造器的颜色参数 —— 这叫"把 alpha 烘进状态"，代价是**改的时候全局生效**，收益是不需要任何 `@Redirect`/`@Overwrite`，也不碰原版逻辑。

**出厂配置 `required:false` + `defaultRequire:0`**：目标对不上只是"没有动画"，不崩游戏。代价是**静默失效**，所以 `tools/check_mixins.py` 在构建期把"注入目标不存在"变成硬错误。

### 3.3 关键设计手法（值得保留的）

- **"遮罩静止"不靠类型判断，靠抵消**：在遮罩绘制期间反向 `translate`，既不动原版状态也不用反射。
- **`@ModifyVariable` 的 `method` 全部写完整描述符**：26.3 的 `BlitRenderState` 有两个构造器（姿态 `Matrix3x2f` / `Matrix3x2fc`），写 `"<init>"` 会同时匹配两个、必有一个找不到目标 → Mixin 判定失败 → 启动崩溃。**这正是原版同名模组在 26.3 上崩掉的原因**（见 `bedrock-ui-animations-分析报告.md` §6.1）。
- **打断接续用二分反解**：关闭动画播到一半又打开时，按当前可见透明度反解新曲线进度并回拨起点。曲线可配置，所以用二分 40 次而不是解析求逆。
- **原地淡变挂在 `extractSlot` 上**：这是唯一能区分"创造模式物品列表"和"玩家快捷栏"的注入点。
- **零反射**（模组本体）：只依赖 `Screen`/`Gui`/`Hud` 等稳定钩子。唯一的反射是读 `LevelLoadingScreen.reason` **用于打日志**（`UiTransitions.java:1441`），失败返回 `"?"`。

## 5. 验证体系（项目最强的地方）

**单一入口** `tools/verify_all.py`，**7 关串行、任一失败立即停下并返回非 0**（`neotest` 由 `--neoforge` 追加为第 8 关）：

| # | 关卡 | 命令 | 阻止什么 |
| --- | --- | --- | --- |
| 1 | 编译 | `tools/compile.py --release 21` | 类型错误；**优先用本机真实 NeoForge API**，拿不到才退回桩类并明确打印用的哪种 |
| 2 | Mixin 注入目标核对 | `tools/check_mixins.py --quiet` | `defaultRequire=0` 下"目标对不上 → 静默无动画"被提前变成硬错误 |
| 3 | 状态机断言 | `tools/run_verify.py` | 打断接续、逐格渐变、遮罩静止、物品通道、分类曲线、果冻、overlay 降级 |
| 4 | 生成物一致性 | `ui-transitions/gen_verify.py --check` | **只改生成物不改模板**（verify-uit 是生成的） |
| 5 | 共用代码纯净性 | `tools/check_shared_code.py --quiet` | 共享代码里引用加载器专属类（一犯就整屏空白） |
| 6 | 翻译完整性 | `tools/check_lang.py --quiet` | 代码里用的键在中英两份 lang 里缺失/不一致 |
| 7 | 打包 + 产物纯净性 + **元数据一致性** | `ui-transitions/build_jar.py` | **硬闸**：产物出现 `com/uitransitions/` 之外的 class 直接非 0 退出；元数据缺键 / `modId` 不一致 / **`neoforge.mods.toml` 的 `version` 与 `fabric.mod.json` 不一致（10-07 新补，`:55-62`）** / MANIFEST 与元数据不一致 / 缺图标 |
| 8 | 真实 NeoForge 启动 | `neotest/neoforge_test.py`（`--neoforge`） | "离线全绿但 FML 拒绝加载"这一类（1.3.0~1.4.0 的 JPMS 包冲突） |

各层**能证明什么 / 证明不了什么**：

| 层 | 证明 | 证明不了 |
| --- | --- | --- |
| 编译 | 类型正确；`compile.py` 只编译 `src/**`，**不编译 verify-uit / visualtest** | 桩类是真 API 的假设（第 8 关存在的唯一理由） |
| 注入核对 | 每个 `@Mixin`/`@Inject` 目标方法**真的存在**（目标 jar 固定为 `build/mc/client-26.3.jar`；今天实测 **17 个 mixin / 52 个注入点全部命中**），且**被注入方法自己的字节码里真的含有那个 invoke** | `ordinal` / `index` / `argsOnly` / `shift` 一个都看不见 —— **ordinal 指错但能解析到某个 int 参数时，注入照样成功、构建照样绿，只是把 alpha 乘到了别的参数上（错的是画面不是构建）** |
| 状态机断言 | 数值行为（真实 JVM）。**但只编译 `UiTransitions.java` + `TransitionConfig.java` 两个源文件**，无 classpath | 其余源码、mixin 应用、渲染效果 |
| 真机截图 | 像素级现象（驱动逐条打 `✅/❌` 日志） | **仍然没有失败判定**：`visual_test.py` 只在游戏进程非 0 退出时失败，日志里的 `❌` 依旧不触发失败（`:374-382`）。已改进的是可见性 —— 汇总现在认 `❌` 并打印"驱动共做出 N 条带结论的检查"（`:288-306`），所以**必须人工读日志**这一点没变 |
| NeoForge 实机 | FML 是否接受这个 jar（判据 = 日志出现 `已注册 NeoForge 配置入口`） | 画面；且 `已检测到 Cloth Config` 那条标记**不参与判定**（只打印） |

**五条必须记住的操作事实**：

1. 模组日志走 `System.out`，**不进 `logs/latest.log`**（那里只有 Log4j）—— 抓日志必须抓进程 stdout。`neotest/neoforge_test.py` 同时抓两份，正是为这个。
2. `verify-uit/VerifyTransitions.java` 与 10 个桩类**是 `gen_verify.py` 生成的**，第 4 关拦"只改生成物不改模板"。
   但 **`VerifyAdvanced.java`（~90 条断言 / 16 个分组，含曲线编辑器模型）不在生成模板里**，可以直接编辑、不会被第 4 关拦 —— 它是新增离线断言最自然的落点。实现侧本轮已按此把多点增删拖、部位曲线分离、分类时长跟随语义全加在 `VerifyAdvanced`，**零模板成本**。
3. `verify_all.py` 自己的 docstring **已过时**（写 6 关，实际 7 关 + `--neoforge` 第 8 关）—— 实现侧 10-07 已订正为"以 `stages` 为准"。
4. **`--release 21` 只对 `compile.py` 生效**；`run_verify.py` 与 `visual_test.py` 里硬编码 21。
5. **验证一个闸时，必须确认它是因为你预期的那个原因而失败的。** 实现侧补版本号闸时踩过：用 PowerShell `Set-Content` 写测试文件被加了 BOM → TOML 先解析失败，**退出码同样是 1**，差点当成"闸生效"收工。

## 6. 风险与债务清单

### 6.1 结构性（本次架构设计针对的）

| # | 问题 | 证据 | 后果 |
| --- | --- | --- | --- |
| S1 | **37 个静态可变状态共用一个 alpha** | `WINDOW_ALPHA` 被 7 条路径读写；为此有 `FRAME_ALPHA`/`FRAME_FADE_ALPHA`/`PIP_FRAME_ALPHA` 三个近似变量 + 大段"为什么不能用那个"的注释（`UiTransitions.java:54-82`、`360-370`、`596-601`） | 新功能必须理解全部既有路径才能正确改一个值 |

| S3 | **矩阵压栈靠条件分支保证配对** | `beginLayer` 注释记录了真实事故：压栈曾只在部分分支执行 → "少压一次等于多弹一次，矩阵栈错位，把裁剪区算成 0 高/0 宽而崩在渲染阶段"（`400-405`） | 同类 bug 会重现；缺一条"帧末 depth==0"的断言 |

## 7. Git 历史读出来的项目节奏

最近 30 次提交里，**约 40% 是"修上一版引入的回归"**，且几乎每次都有明确的实机反馈来源：

| 现象 | 根因 | 修复 |
| --- | --- | --- |
| 快捷栏跟着渐变 | 1.4.0 把物品兜底从 `FRAME_ALPHA` 改成 `PIP_FRAME_ALPHA` 之后的回归 | 连 `PIP_FRAME_ALPHA` 一起冻住 |
| 关闭动画留残影 | 物品透明度在渲染阶段被复位成 1 | 引入 `PIP_FRAME_ALPHA`（跨阶段保留） |
| 手机上曲线编辑器点不开 | 自绘区域被控件抢先消费 | 多点编辑改成不依赖拖动 |
| 裁剪区交出空矩形 | 矩阵栈错位 | 裁剪区永不交出空矩形 + 尺寸变化兜底 |
| NeoForge 完全不启动 | **桩类被打进 jar** → JPMS 包冲突 | 优先用本机真实 API + 产物纯净性硬闸 |
| 模组列表配置页空白 | NeoForge 旧 API 被移除 | 改 `registerExtensionPoint` |
| 快捷键/字幕/提示框跟着动 | 注入点选在调用方而非被调方法 | 改挂 `Hud` 层 |
| **版本号三处不一致却没被拦** | `build_jar.py` 只比 `modId`、从不读 toml 的 `version` | 10-07 10:28 补成真闸（`f352383`）——**这条是本次分析提出的，实现侧当天修掉** |
| **闸失败了但不是因为预期原因** | PowerShell `Set-Content` 给 TOML 加了 BOM → 解析先失败 | 改用 `File.WriteAllText` + `UTF8Encoding(false)` 才验准 |

**这份历史本身就是本次架构设计的论据**：列表里有 5 条属于"共享全局状态导致 A 影响 B"。README 第 5.5.2 节已经把教训写成十条方法论（其中"断言里的预期值也会写错"、"测试里的行号写错看起来和代码坏了完全一样"两条尤其诚实）。

**一条来自本轮协作的补充**：最近两次提交（`788f2ca` 1.5.01 版本规则、`f352383` 版本号闸）都是**收到分析报告后当天做的**，其中版本号闸的缺口是分析报告指出的。这说明这条"设计 → 实测 → 反馈 → 修"的回路是通的 —— 也就是本次架构落地最有利的条件。
