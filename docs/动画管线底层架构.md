## 1. 为什么现在需要一个底层

`UiTransitions.java` 现在 1456 行代码（含空行 1561 行），一个类里躺着 **37 个静态可变状态**。按类型精确清点（`ui-transitions/src/com/uitransitions/UiTransitions.java:34-153`、`952-956`、`1133-1137`）：

| 类型 | 个数 | 是哪些 |
| --- | --- | --- |
| `ThreadLocal<Boolean>` | 3 | `BYPASS` `BACKGROUND_PUSHED` `STATIC_REGION` |
| `ThreadLocal<Float>` | 5 | `WINDOW_ALPHA` `LAYER_SHIFT` `LAYER_ALPHA` `PIP_SHIFT` `PREVIEW_ALPHA_SAVED` |
| `ThreadLocal<Object>` | 3 | `PUSHED_SCREEN` `BACKGROUND_EXTRACTOR` `BACKGROUND_SCREEN` |
| 弱引用/标识映射 | 7 | `ITEM_ALPHAS` `OPEN_START` `CLOSING` `FINISHED` `TAB_SWITCH` `LAST_SCROLL` `GRID_BOUNDS` |
| 并发键集 | 2 | `REPORTED` `SKIP_LOGGED` |
| 原子标志 | 1 | `EFFECTIVE` |
| 帧级 volatile 标量 | 11 | 含 `FRAME_ALPHA` `FRAME_FADE_ALPHA` `PIP_FRAME_ALPHA` `TEXT_ALPHA` 与聊天/遮罩计时 |
| 计数器 | 2 | `VEIL_DRAW_LOGGED`（int）、`lastScreenChange`（String） |
| **合计** | **37** | 一个类、无实例 |

最近两次提交的形态说明了趋势：

| 日期 | 提交 | 新功能是怎么加进去的 |
| --- | --- | --- |
| 1.5.0 | `逐部位曲线 / 多点曲线 / 排除界面` | `Part` 枚举 + 4 个 `EnumMap` + 配置页 + 双语键 |
| 10-07 | `界面分类模型 + 聊天栏新消息淡入` | `UiCategory` 枚举 + 4 个 `EnumMap` + **`UiTransitions` 又加了 6 个静态字段** |

第二次加功能时，`UiTransitions` 里新增了 `chatFadeStartNanos` / `chatFadeActive` / `chatLineCount` / `chatContentHash` 四个字段和 6 个方法。**这就是本设计要终止的模式**：功能状态寄生在全局类里，第三个、第四个功能会继续叠加。

四个具体病灶（都能在现有代码里指到行）：

1. **37 个静态可变状态共用一个 alpha**。`WINDOW_ALPHA` 被贴图、物品、画中画、遮罩、字幕、预览、快捷栏七条路径读写，谁最后写谁生效。为此不得不写 `PIP_FRAME_ALPHA` / `FRAME_ALPHA` / `FRAME_FADE_ALPHA` 三个语义相近的帧级变量，并用大段注释解释"为什么这里不能用那个"（`UiTransitions.java:54-82`、`596-601`）。**这类注释是缺抽象的症状，不是文档。**
2. **矩阵压栈/弹栈的正确性靠条件分支维持**。`beginLayer` 里有一段注释记录过真实事故：压栈曾经只在某些分支执行，导致"少压一次等于多弹一次，整个渲染管线的矩阵栈错位，把裁剪区算成 0 高/0 宽而崩在渲染阶段"（`UiTransitions.java:400-405`）。
3. **`premultiplied` 是全局标志而不是渲染通道属性**。`beginItemSubmit` 置 `PREMULTIPLIED=true`（`604`），`endItemSubmit` 复位（`613`）。窗口内任何文字/矩形都会走预乘缩放分支 —— 这是"物品提交阶段恰好又画了别的东西"就会出错的结构。
4. **加一个"部位"要改 5 个地方**：`Part` 枚举、两个 `EnumMap`、配置读写、Cloth 配置页、中英双语键。加第四个功能时，前 3 条会一起恶化。

**验收标准（本设计是否成功的唯一判据）**：
> 下一个新动画（例如"拾取物品时快捷栏弹一下"）的 diff 里，`UiTransitions.java` 不出现。

## 2. 分层模型

```
┌─ ④ 适配层  UiTransitions（门面，静态方法签名一律不变）
│             ← 只做转调，不再持有任何动画状态
├─ ③ 合成层  FrameContext / BandStack / Channel
│             帧级上下文 + 严格配对的区间栈 + 显式的颜色通道
├─ ② 状态层  ScreenActors（每屏一个 Actor）/ Tween / Continuation
│             谁在动、动到哪、被打断了怎么接
└─ ① 数学层  Timeline / Easing / AnimationSpec / ColorMath / Clock
              纯函数，零 Minecraft 依赖 → 可以脱离游戏全部离线断言
```

**依赖方向只能向上**：① 不认识 ②，② 不认识 Screen 的渲染细节，③ 不认识具体功能。`Effect` 是唯一允许跨层的扩展点（见 §6）。

## 3. 核心类型

### 3.1 ① 数学层（纯 Java，零 MC 依赖）

```java
package com.uitransitions.anim;

/** 时间源。测试可注入假时钟，这是所有断言可重复的前提。 */
public interface Clock { long nanos(); }

/** 缓动函数。**唯一的曲线抽象**：现有 Curve / CUSTOM / MULTI 三种实现统一到它下面。 */
public interface Easing {
    float ease(float t);            // t ∈ [0,1] → 值域可越界（back 会 >1）
    default float inverse(float v) { // v = ease(t)，二分反解；打断接续用
        float lo = 0f, hi = 1f;
        for (int i = 0; i < 40; i++) { float m = (lo + hi) * 0.5f;
            if (ease(m) < v) lo = m; else hi = m; }
        return (lo + hi) * 0.5f;
    }
}

/** 一段动画的不可变描述。取代散落的「时长 + 曲线」两处读取。 */
public record Tween(long startNanos, long durationNanos, Easing easing, float from, float to) {
    public float progress(long now) { ... }           // clamp01((now-start)/duration)
    public float value(long now)    { ... }           // lerp(from, to, ease(progress))
    /** 打断接续：保持当前可见值不跳变，反解出新的起点 */
    public Tween continueFrom(long now, float visible, long newDuration, Easing newEasing) { ... }
}
```

`Tween.continueFrom` 是把现有 `solveProgress` + `backdateNanos` + `Curve` 三处逻辑（`UiTransitions.java:1316-1339`）收进一个可单测的纯函数。**打断接续的数学在这里被证明一次，而不是每次新功能重新推一遍。**

### 3.2 ② 状态层

```java
public enum AnimKind { OPEN, CLOSE, IN_PLACE }   // IN_PLACE = 标签切换 / 滚动 / 聊天淡入

/** 动画宿主 = 谁在动。Screen 是宿主，但聊天栏、快捷栏、传送门遮罩、预览也是宿主 ——
 *  这是现有代码最大的概念缺失：不是所有动画都挂在 Screen 上。
 *  **宿主与图标层（Band）是两个正交维度**，见 §3.3.1。 */
public enum Host { SCREEN, HUD_CHAT, HUD_HOTBAR, HUD_SUBTITLES, HUD_VEIL, PREVIEW }

public final class Actor {
    Host host();
    AnimCategory category();                         // 宿主属于哪一类（决定默认曲线与时长）
    AnimKind kind();
    boolean idle();                                  // 已就位：渲染路径应走快路径
    float progress(long now);
    Tween tween(Band band);                          // 该图层自己的那段（支持逐部位曲线）
    Actor retarget(AnimKind next, long now, float visible);   // 打断：不跳变
}

/** 一个宿主一个 Actor。**聊天栏也是宿主**，于是它的"内容指纹触发重新计时"有地方放，
 *  不必再往全局类里加 4 个静态字段。 */
public final class Actors {
    Actor actorOf(Host host);                        // 找不到就懒建（等价于现在的 OPEN_START 懒启动）
    void forget(Host host);
    void sweep();                                    // 清掉已结束且非当前的 Actor
}
```

**关键改变**：`progress(screen)` 现在的副作用（在 `OPEN_START` 里懒创建一个 `Open`，`UiTransitions.java:1358-1362`）被收进 `actorOf`，语义显式（"取不到就建一个刚开始的"），不再是隐式写状态。

**`chore`：聊天栏作为宿主的形态**。现在聊天淡入的状态是 4 个 `volatile` + 一个"内容指纹变了就重置起点"的裸计时器（`UiTransitions.java:952-956`、`1025-1039`）。新模型里它是 `Actor(HUD_CHAT, AnimCategory.CHAT, IN_PLACE)` 上一个 `Tween`：指纹变了就 `actor.retarget(IN_PLACE, now, visible)` —— 与"打开被打断"走**同一条**接续逻辑，不再有一份独立的计时实现。

### 3.3 ③ 合成层

> **本节按实现侧回执修订过**（见 §11）。原稿有两个建模错误：把 HUD 宿主当成图层、以及把"当前在画谁"漏出了契约。

#### 3.3.1 两个正交的维度：宿主（谁在画）与区间（画在哪一层）

**宿主不是区间。** 屏幕与 HUD 是**两个不相交的宿主**；聊天栏、快捷栏是 HUD 上的绘制窗口，不是屏幕内部的图层。把 `Chat`/`Hotbar` 与 `PANEL`/`TEXT` 并列会诱导人写出"聊天和底板同级"的错误模型。

```java
/** 区间 = **屏内图层**，一一对应现在的 Part。宿主不进这里。 */
public enum Band { PANEL, DIM, ITEMS, TEXT, SUBTITLES, TAB, PORTAL }

/** 宿主 = 谁在画。屏幕、HUD 的各窗口各是一个宿主。 */
public enum Host { SCREEN, HUD_CHAT, HUD_HOTBAR, HUD_SUBTITLES, HUD_VEIL, PREVIEW }

/** 动画类别 = **数据维度**（曲线 + 时长），不是行为入口。见 §5.4。 */
public enum AnimCategory { CHAT, CREATIVE, GAME_MENU, CONTAINER, PORTAL, OTHER }
```

映射：现在的 `Part.CHAT` / `Part.HOTBAR` 并不存在（它们分别是"聊天宿主"和"对快捷栏施加 pin"），所以 `Band` 只需要 **7 项**，与 `Part` 一一对应；`Host` 是新增的维度。

#### 3.3.2 作用域（Scope）：让"当前在画谁"成为显式契约

`applyAlphaText` 被**两个互不相干的场合**共用：屏幕文字（读 `TEXT_ALPHA`）与聊天栏文字（要在其上再乘聊天淡入系数）。原稿的 `Channel.apply(int argb, float alpha)` 是纯函数、不带作用域，`chat.fade` 能算出系数却**没有任何机制把它送到通道层** —— 这是原稿的实质缺陷。

```java
public final class FrameContext {
    long frameNanos();
    Host scope();                                   // 此刻在画哪个宿主
    <T> T withScope(Host h, java.util.function.Supplier<T> body);   // 严格配对，可断言

    /** 曲线解析：**部位覆盖 → 类别覆盖 → 全局**（与现在 UiTransitions.curveFor 的三级回退等价） */
    Easing easing(Band band, AnimKind kind);
    /** 时长解析：类别覆盖 → 全局（与现在 openDurationFor/closeDurationFor 等价） */
    long durationNanos(AnimKind kind);

    /** 帧级值：**跨阶段通信**。取代 8 个 ThreadLocal **+ 3 个帧级 volatile**（见 §6）。 */
    float frameValue(FrameValue key);
    void  setFrameValue(FrameValue key, float v);

    /** 提交阶段（渲染线程后段）读的"最终呈现值" */
    float presentedAlpha(Band band);
}

/** 跨阶段 / 跨 Effect 的帧级值，显式枚举，取代 volatile 三兄弟与几个 ThreadLocal */
public enum FrameValue {
    CONTENT_ALPHA,          // ← FRAME_ALPHA
    CONTENT_PRESENTED,      // ← PIP_FRAME_ALPHA（提取写、渲染阶段读）
    IN_PLACE_ALPHA,         // ← FRAME_FADE_ALPHA（原地淡变是否活跃，hotbar.pin 的触发信号）
    LAYER_SHIFT,
    ITEM_TAG                // 物品登记表（提取阶段写、提交阶段读）
}

/** 严格配对的区间栈。代替 ThreadLocal<Boolean> PUSHED / BACKGROUND_PUSHED 那一套。 */
public final class BandStack {
    void push(Band b, GuiGraphicsExtractor extractor);   // 记录：我压了栈
    void pop(Band b, GuiGraphicsExtractor extractor);    // 只有 push 成功过才弹
    boolean isOpen(Band b);
    int depth();                                          // **断言用**：帧末必须为 0（区间 + 作用域各一份）
    void resetAtFrameStart();                             // 兜底：上帧异常退出的残留在这里清掉
}

/** 颜色通道 —— 显式取代 ThreadLocal<Boolean> PREMULTIPLIED（当前的真实缺陷） */
public enum Channel {
    BLIT(false),        // 普通贴图：只调 alpha
    RECT(false),        // 纯色块：只调 alpha
    TEXT(false),        // 文字：走 TEXT 区间透明度 + 当前宿主的作用域修正
    ITEM(true),         // 物品图集：预乘 alpha，RGB 一起缩放
    PIP(true);          // 画中画贴回：预乘

    boolean premultiplied();
    /** **带上下文**：通道要能问"我在谁的窗口里"，这正是聊天淡入需要的 */
    int apply(FrameContext ctx, int argb);
}
```

**两处修正的由来**：

- `PREVIEW` **不再是 `Channel`**。曲线编辑器的预览用的是 `pushPreviewAlpha` / `popPreviewAlpha` 手动配对，天然属于作用域（`ctx.withScope(Host.PREVIEW, …)`），加个枚举项解决不了它。
- `Channel.apply` **必须带 `FrameContext`**。聊天淡入就是靠"通道能问到当前宿主"才成立的；原稿的纯函数签名把他正在写的功能挡在门外。

**通道化修掉了什么**：现在 `applyAlphaText` → `modulate(color, TEXT_ALPHA.get())` → 里面却读全局 `PREMULTIPLIED`（`UiTransitions.java:549`）。物品提交窗口里画出来的文字会被当成预乘颜色做 RGB 缩放。新模型下 `TEXT.premultiplied()` 永远是 `false`，与谁在压栈无关。

#### 3.3.3 帧级值的写入者 → 读取者（必须显式建模）

有一类依赖**不是**"Effect 产生值 → 通道消费"，而是**一个功能产生帧级值、另一个功能读它当触发信号**。漏掉它，第 5 步按表搬会**静默失效**：

| 帧级值 | 谁写 | 谁读 | 漏掉的后果 |
| --- | --- | --- | --- |
| `IN_PLACE_ALPHA` | `tab.inplace`（原地淡变开始） | **`hotbar.pin`**（`pauseForTabStatic` 用 `FRAME_FADE_ALPHA >= 0.999F` 判断要不要介入，`UiTransitions.java:832`） | 快捷栏不再固定 → `VerifyAdvanced` 会红 |
| `CONTENT_PRESENTED` | 内容层区间 | `Channel.ITEM`（提交阶段）/ `Channel.PIP` | 关闭动画里物品不跟着淡，留残影（1.4.0 的真实回归） |

**契约要求**：`FrameValue` 是显式的枚举，Effect 通过 `ctx.frameValue(...)` 读、`ctx.setFrameValue(...)` 写，**写入者与读取者都必须在文档里登记**。§5 的 Effect 表每一行都要标出"写哪些 / 读哪些"。这是原稿完全没提的一环。

### 3.4 ④ 适配层：`UiTransitions` 变成纯门面

**签名一个都不改。** `ScreenMixin`、`GuiMixin`、七个渲染状态 mixin、`HudSubtitleMixin`、`HudVeilMixin`、`ChatFadeMixin`、`ChatFadeNoteMixin`、`SlotFadeMixin`、`HotbarTabExcludeMixin`、`PictureInPictureRendererMixin`、`OversizedItemRendererMixin` **全部不动**。

```java
public final class UiTransitions {
    private static final Engine ENGINE = new Engine(System::nanoTime, TransitionConfig::asSpec);

    public static boolean interceptSetScreen(Gui gui, Screen target) { return ENGINE.onSetScreen(gui, target); }
    public static void beginBackgroundLayer(Screen s, GuiGraphicsExtractor e) { ENGINE.beginBand(Band.PANEL, s, e); }
    public static int applyAlphaBlit(int color) { return ENGINE.apply(Channel.BLIT, color); }   // 内部取当前帧上下文
    public static int applyAlphaText(int color) { return ENGINE.apply(Channel.TEXT, color); }
    // ...其余方法逐条转调，不再有字段
}
```

这一层存在的唯一理由是**移动端兼容**：`verify-uit/VerifyAdvanced.java` 实测有 **212 处**、`VerifyTransitions.java` **25 处** `UiTransitions.xxx` 直接调用（计法：匹配 `UiTransitions.<方法>(` 的调用点）。它们是这个项目最强的资产（逐条断言了打断接续、逐格渐变、遮罩、物品通道）。门面让它们**全部继续有效**，同时也是迁移期的安全网 —— 新旧实现可以逐条对比。

## 4. 一帧的执行契约

现有三类混入点恰好对应三个阶段。**契约是"每帧三个阶段各一次，阶段内区间严格嵌套"**：

| 阶段 | 触发 | 允许做的事 | 禁止 |
| --- | --- | --- | --- |
| ① EXTRACT | `ScreenMixin` 在 `extractRenderStateWithTooltipAndSubtitles` 的 6 处注入 | 开区间、压栈、平移、记录物品登记 | 提交任何绘制 |
| ② SUBMIT | `GuiRendererMixin` / `PictureInPictureRendererMixin` / `OversizedItemRendererMixin` | 读 `presentedAlpha`、按通道施加 | 改区间结构、开新区间 |
| ③ FRAME_END | `endScreenFrame` / `HudVeilMixin` RETURN | 清帧、断言 `BandStack.depth()==0` **且作用域栈也为 0** | 留下任何状态 |

现有代码的 `Frame` 边界是隐式的（`beginContentLayer` 里那句 `FRAME_FADE_ALPHA = 1.0F;  // 新的一帧开始`，`UiTransitions.java:317`）。新模型把它变成显式的 `ENGINE.beginFrame()` / `endFrame()`，并带两条**兜底断言**：

```java
// endFrame 里（仅 -Duitransitions.assertPipeline=true 时生效，出厂零开销）
assert stack.depth() == 0 : "区间未配对，矩阵栈会错位（历史上真的崩过）";
assert ctx.presentedAlpha(Band.ITEMS) >= 0f : "帧末残留透明度会把 HUD 物品淡掉";
```

## 5. `Effect`：新功能的唯一扩展点

```java
public interface Effect {
    String id();                                     // 配置键前缀 + 日志名
    /** 出手顺序：小的先算，大的覆盖。静态区间（遮罩/字幕）用负值，
     *  跟随动画的用 0，纠正类（快捷栏固定）用正值。 */
    default int priority() { return 0; }

    /** 每帧、每区间问一次。返回 null = 不介入（零开销快路径）。 */
    Contribution contribute(FrameContext ctx, Band band);

    /** 动画开始/结束时的一次性通知（可选） */
    default void onRetarget(Host host, AnimKind from, AnimKind to) {}
}

/** 一个区间的最终呈现。compose 顺序固定：base → 各 Effect 按 priority 叠加。 */
public record Contribution(Float alpha, Float shift, Boolean pinToVanilla) {
    Contribution multiply(Contribution other, float weight) { ... }
}

/** 效果链：按 **Band + Channel 解析行为**。
 *  注意：**Category 不是链的入口** —— 它是数据（曲线 + 时长），见 §5.2。 */
public final class EffectChain {
    static EffectChain forBand(Band band);
    Contribution compose(FrameContext ctx, Band band, Channel ch);
}
```

**十个现有行为逐个映射到 Effect**（迁移时一行一行对着搬，行为必须完全一致）。**每一行必须标出它读/写的帧级值**（§3.3.3）—— 原稿漏了这一列：

| Effect id | priority | 作用域 | 写 | 读 | 现在散落在哪 |
| --- | --- | --- | --- | --- | --- |
| `panel.slide` | 0 | SCREEN | `LAYER_SHIFT` | — | `shift()` / `beginLayer` |
| `panel.fade` / `items.fade` / `text.fade` | 0 | SCREEN | `LAYER_SHIFT` `CONTENT_ALPHA` `CONTENT_PRESENTED` | — | `alpha(screen, progress, part)` |
| `dim.static` | −10 | SCREEN | — | `LAYER_SHIFT` | `pauseForStaticRegion` |
| `subtitles.static` | −10 | HUD_SUBTITLES | — | `LAYER_SHIFT` | `pauseForHud` |
| `subtitles.follow` | −9 | HUD_SUBTITLES | — | — | `animateSubtitles` 分支 |
| `tab.inplace` | 0 | SCREEN | **`IN_PLACE_ALPHA`** | — | `beginTabContent` |
| `slot.ramp` | 0 | SCREEN | — | `IN_PLACE_ALPHA` | `beginSlotFade` / `slotFloorAlpha` |
| `hotbar.pin` | +10 | HUD_HOTBAR | — | **`IN_PLACE_ALPHA`** ← **关键依赖** | `pauseForTabStatic` |
| `portal.veil` | 0 | HUD_VEIL | — | — | `startPortalVeil` / `veilAlpha` / `drawPortalVeil` |
| `chat.fade` | 0 | **HUD_CHAT** | — | `AnimCategory.CHAT` 曲线 | **上一条提交刚加的 6 个静态字段** ← 第一个迁移目标 |

`chat.fade` 的接法（按 §3.3.2 的作用域模型，这就是他要求的那个能力）：

```java
// 1) 计时侧（ChatFadeNoteMixin → Hud.extractChat）：内容指纹变了就重开一段，
//    走与"打开被打断"完全相同的接续逻辑（§3.2）。曲线取 AnimCategory.CHAT。
Actor chat = actors.actorOf(Host.HUD_CHAT);
chat.retarget(AnimKind.IN_PLACE, now, chat.visibleAlpha());

// 2) 施加侧（ChatFadeMixin → ChatComponent.extractRenderState）：把绘制窗口标出来
ctx.withScope(Host.HUD_CHAT, () -> chatComponent.extractRenderState(extractor));

// 3) Channel.TEXT.apply 里（这是原稿缺的那一环）：
float a = ctx.alphaFor(Band.TEXT);
if (ctx.scope() == Host.HUD_CHAT) a *= chat.visibleAlpha();   // ← 显式，不再靠 chatFadeActive 全局标志
return ColorMath.apply(argb, a, Channel.TEXT.premultiplied());
```

这样 `applyAlphaText` 里那段"聊天乘子"（`UiTransitions.java:528-531`）就有了正当归属，第 2 步搬通道时不会把它丢掉。

### 5.1 `Band` 之外的宿主：`HOTBAR` 与 `CHAT` 不是区间

原稿把 `CHAT` / `HOTBAR` 放进 `Band` 是错的（见 §3.3.1）。正确的表述：

- **`Band` 只留屏内 7 个图层**（与 `Part` 一一对应）；
- **`HOTBAR` / `CHAT` / `SUBTITLES` / `PREVIEW` 是宿主**，走 `Host` + `withScope`；
- `hotbar.pin` 的语义是"**对 `HUD_HOTBAR` 这个宿主 pin 住**"，不是"对某个区间乘一个值"；
- `subtitles` 两行同理：它是 HUD 上的宿主，只是**恰好画在背景层区间内部**，所以它既要作用域（宿主）又要读区间位移（`LAYER_SHIFT`）—— 这正好证明两个维度都需要。

### 5.2 分类是数据，不是行为（**按实现侧要求修正**）

原稿的 `EffectChain.forCategory(c)` 是错的：那样每加一个分类就得加一个 Effect，回到"加枚举要改 5 个地方"。

**正确形态**：`AnimCategory` 只作为 `FrameContext` 的**查询维度**（曲线 + 一对时长），`EffectChain` 只按 `Band + Channel` 解析行为。

```java
// 分类的解析链与现在 UiTransitions.curveFor / openDurationFor 完全等价：
//   曲线：部位覆盖 → 类别覆盖 → 全局
//   时长：类别覆盖 → 全局
ctx.easing(Band.ITEMS, AnimKind.OPEN);   // 内部就是走 category 覆盖
ctx.durationNanos(AnimKind.CLOSE);
```

于是"配置页按分类分选项卡"（他下一条要做的功能）**只需要动数据表**：`TransitionConfig` 加一行分类的曲线/时长，**不需要新增任何 Effect**。这正是 §1 的验收标准在分类维度上的体现。

## 7. 测试契约（与 `tools/` 的关系）

现有验证链是 **`tools/verify_all.py` 的 7 关串行**（编译 → Mixin 目标 → 状态机断言 → 生成物一致性 → 共享代码纯净性 → 翻译完整性 → 打包纯净性；`--neoforge` 追加真机第 8 关）。新架构必须让**离线断言覆盖面扩大**，而不是平移。三条硬性要求：

1. **`ScreenActors` / `Tween` / `Easing` / `ColorMath` 必须能在没有 Minecraft 的 JVM 里跑完**。它们零 MC 依赖，`tools/run_verify.py` 直接加断言，不需要桩类。
2. **新增栈纪律断言**（这一类 bug 历史上有过，且现象是崩溃）：
   - 每个 `push` 都有配对 `pop`；帧末 `depth()==0`；
   - 异常路径（区间内抛异常）之后 `depth()` 仍为 0；
   - 同一 Band 嵌套 push 只允许一层。
3. **新增帧隔离断言**：两个线程各自跑一帧，`FrameContext` 不互相污染；`Engine` 可重复 `beginFrame/endFrame` 无残留。

**三条必须遵守的既有约束**（都是工具链的硬事实，不是偏好）：

- `tools/check_mixins.py` 能证明"目标方法存在 + **被注入方法自己的字节码里真的含有那个 invoke**"（实测：17 个 mixin / 52 个注入点全部命中），但它**看不到 `ordinal` / `index` / `argsOnly` / `shift`**。所以 ordinal 指错但可解析时，注入成功、构建全绿、只是把 alpha 乘到了别的参数上 —— **错的是画面，不是构建**。本设计因此刻意**不改任何 mixin 文件**，把这个风险留在原状而不是扩大。
- `tools/run_verify.py` **只编译 `UiTransitions.java` + `TransitionConfig.java`**（加 10 个桩类，无 classpath）。所以 §8 第 1 步的数学层必须零 MC 依赖才能进这条链 —— 带 `net.minecraft` 的类连编都编不过。
- 生成与漂移检查的边界要说清：**`verify-uit/VerifyTransitions.java` 是 `gen_verify.py` 生成的**（改它必须先改模板，否则 `--check` 报漂移）；而 **`VerifyAdvanced.java` 不在生成模板里**，可以直接编辑、不会被漂移检查拦下。**新增离线断言优先放 `VerifyAdvanced`**，成本最低。

### 8.5.5 由独立核查发现的、原注释未覆盖的事实

1. **`nextStratum()` 是官方的层边界**：26.3 原生在每层之间切 stratum，`Band` 对应的是引擎真概念，不是自定义抽象。另有 `blurBeforeThisStratum()`（模糊在特定 stratum 之前应用）。
2. **`GuiRenderState` 不是顺序栈**：内部是 `List<Node>` + `current`，且 `findAppropriateNode(ScreenArea)` / `navigateToAboveHighestElementWithIntersectingBounds(ScreenRectangle)` 会**按边界相交往上找节点**；单元还**按类型分列表**（`elementStates`/`glyphStates`/`itemStates`/`textStates`/`picturesInPictureStates`）并有 `sortElements(Comparator)`。
   → **元素不是按提取顺序渲染的**。这从引擎层面解释了为什么物品必须走 `ITEM_ALPHAS` 登记表（提取登记 → 提交套用）、为什么 `PIP_FRAME_ALPHA` 必须跨阶段保留。任何"按提取顺序写 alpha 就按序生效"的假设都不成立。
3. **`pose` 是渲染状态的构造参数**：说明 `@ModifyArg index=2`（画中画叠位移）是引擎支持的正常手段，不是 hack；但也意味着**改这些构造参数会与官方的排序/边界逻辑交互**，属于高风险区。

### 8.5.6 证伪：`ScreenMixin` 的"已知边界"清单有 3/8 条不成立

`ScreenMixin` 的类注释声称这些界面覆写了背景方法、因而绕过方法级抵消：
`WinScreen` / `WorldOptionsScreen` / `StatsScreen` / `CreateWorldScreen`（`extractMenuBackground`）、`DebugOptionsScreen`（`extractBlurredBackground`）、`TitleScreen` / `GenericMessageScreen` / `LevelLoadingScreen`（`extractPanorama`）。

**对真实 jar 逐个 `javap -p` 的结果**：

| 类 | 注释声称 | 实测 | 判定 |
| --- | --- | --- | --- |
| `WinScreen` | 覆写 `extractMenuBackground` | 确实覆写 | ✅ 成立 |
| `WorldOptionsScreen` | 同上 | 确实覆写 | ✅ 成立 |
| `StatsScreen` | 同上 | 确实覆写（注意真包名是 **`…screens.achievement.StatsScreen`**） | ✅ 成立 |
| `CreateWorldScreen` | 同上 | 确实覆写 | ✅ 成立 |
| `DebugOptionsScreen` | 覆写 `extractBlurredBackground` | 确实覆写 | ✅ 成立 |
| **`TitleScreen`** | 覆写 `extractPanorama` | **不覆写这四个方法中的任何一个** | ❌ **证伪** |
| **`GenericMessageScreen`** | 同上 | **不覆写** | ❌ **证伪** |
| **`LevelLoadingScreen`** | 同上 | **不覆写** | ❌ **证伪** |

**结论与影响**：真正会绕过方法级抵消的只有 **5 个类**，`TitleScreen` / `GenericMessageScreen` / `LevelLoadingScreen` 的乐园背景**本来就被正常抵消**。注释里那三条很可能是从更早版本或凭印象写下的（`PauseScreen` 也常被误认为覆写 `extractPanorama`，实测同样不覆写）。
→ **这条同时是"注释里的结论也要被证实"的又一个例子**：它们不影响正确性（多列了几个类只是让已知边界看起来更大），但会让下一个人基于错的边界做决策。**建议实现侧把这 3 条从注释里删掉**（属于他的文件，由他改）。
